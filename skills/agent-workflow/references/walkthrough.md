# Guided setup and handoff

The setup facilitator owns discovery, configuration and initial routing. EL owns
ongoing execution after handoff; it may later delegate setup changes to a focused
helper. PL owns human/project alignment and attention, with conversation first
and agreed changes relayed at a discussion boundary or on request. Neither role
needs the whole setup conversation. The invoking session normally does the setup
itself, avoiding an extra agent merely to ask the same questions.

## 1. Discover before asking

Establish the intended repository and check its instructions, status, branch,
remotes, worktrees and authoritative entry points. Read relevant current records,
not every historical handoff or skill reference. Identify any existing occupants,
live assignments, held work, grants and accounting records.

Give a short detected-state summary. Distinguish a new setup, adapting an existing
workflow and resuming an interrupted setup. If the current session is in a
different project, resolve the target before mutations or role creation. Never
start the new team inside a read-only example project.

A repeat invocation resumes the current setup. It does not create duplicate
coordination issues, roles, worktrees or budgets. Reconcile contradictory records
against current user decisions; repair obsolete status text rather than allowing
different agents to interpret competing grants.

## 2. Guide only unresolved choices

Ask one question at a time, with the recommended choice and its main tradeoff.
Infer factual answers through inspection and carry forward the user's earlier
decisions. Do not make the user choose implementation details the setup agent can
reasonably handle.

Use the workspace agreement's concerns as a map, not a mandatory questionnaire:

| Concern | Establish if missing |
| --- | --- |
| Purpose | Project direction and the user's next useful conversation |
| Records | Existing goals/decisions, canonical published reference, task/report homes |
| Authority | Initial setup/launch scope and start/review/integration gates |
| Resources | Billing mode, bounded-work allowance policy, applicable explicit limits and observation owner |
| Workspaces | Actual integration targets, ownership and worktree organization |
| Initial contact | Combined PL+EL or separate contacts, according to the project and user |

For a new project without settled product direction, establish enough context to
give leadership a useful first conversation; do not conduct the entire product
design interview during technical setup. For an existing defined initiative,
an EL can be the first contact. Preserve an existing role arrangement unless a
change is needed. Do not instantiate every rank to demonstrate the hierarchy.

Explain the proposed setup concisely as choices settle. Save meaningful decisions
in the chosen canonical record. Keep one current summary rather than a transcript
or a new handoff file for every exchange.

## 3. Prepare the project

Use agent-workspace internally for the mapping and agent-task for the chosen
tracker conventions. Reuse existing structure. Create only the missing agreed
records, links, scoped workspaces and tracking configuration that are necessary
now. A starter asset is optional; do not migrate a working project to use it.

Keep AGENTS.md as a short route to the project agreement. Keep live task/report
state in its authoritative tracker. Record actual branch and workspace ownership
separately from permission to start work or merge it. Workers need not be created
before there is a defined and authorized assignment.

Treat setup and work execution as distinct scopes. A single existing grant may
cover setup and initial role launch; use it without repeated permission requests.
When additional approval is actually needed, prepare the concrete result first,
explain the remaining boundary, and ask here. Do not defer an unresolved setup
choice to a PL/EL simply to end the walkthrough.

## 4. Verify the handoff can work

Use existing authentication and runtime capabilities. Check the selected tracker,
document references and workspace paths. Inspect current tool support for creating,
naming, addressing and waking independent visible sessions; use the available
native operations. Do not assume a sub-agent is human-writable or a newly created
session has the intended cwd.

Check whether another interface owns a session before retrying a failed attach.
If it requires a human UI action, give that exact action and continue the rest
yourself. A necessary UI action is different from asking the user to write a role
brief. Do not promise human input, detach survival or automatic wake from a
successful name change or queue operation.

Record the initial occupants; add helpers and replacements when launched. For
bounded autonomous work, establish its accounting scope and observation owner.
Record each launched session ID immediately, including helpers and replacements.
Collect by those IDs; default session listings can omit native-created sessions.
Preserve cumulative spending within each actual grant, including in-flight work
and closeout. Do not instantiate an observer solely for setup: lightweight usage
collection is sufficient. If ongoing observation needs an agent, give it fresh
focused context and include its cost in the work it supports.

Lightweight local checks do not imply permission for a multi-agent experiment.
Use already authorized launch resources; ask for a missing grant as part of this
walkthrough. An explicitly exhausted scope stays held until its grant changes.
Do not carry that hold into unrelated work or require a numeric setup/project cap.
Starting an interactive leadership role is distinct from dispatching autonomous
work, which needs a bounded allowance. Weekly project allocations are optional.
Describe any test not performed as unverified.

## 5. Create or reconnect the initial contact

Use agent-hierarchy internally. For a new setup, start the agreed initial role(s)
with focused context. Do not automatically promote the setup facilitator into
leadership. A short combined setup/leadership conversation is an option when the
user deliberately prefers it, not the default.

For an existing setup, identify the current occupants and respect live ownership.
Deliver a bounded setup update to the appropriate contact when wake/spending is
authorized; do not recreate the team because the setup session changed.

Generate the handoff from canonical records. Include only:

- Assigned role/scope, relevant supervision and current occupant references.
- The known goal, settled context and concrete immediate objective. For planning,
  specify a brief orientation and the next consequential unresolved question. When
  already scoped, use the next authorized action or actual missing gate instead.
- Authoritative record locations and the actual assigned workspace.
- Current start/review/integration authority and applicable resource policy, with
  grant sources. State when no numeric cap applies to the interactive role.
- Reporting/accounting ownership, relevant runtime limitations and immediate action.

Check that both the launch prompt and its referenced brief request the intended
first response. Do not turn a planning objective into "read, acknowledge, then
wait" or require another user prompt to begin. An explicit pause or acknowledgment-
only diagnostic is an exception; planning authority still grants no autonomous
investigation, implementation, inference or workers.

Deliver the brief yourself and inspect the first useful response as acceptance;
no separate acknowledgment exchange is needed. Unresolved setup defects return
to the facilitator. For routine later activation, use the hierarchy lifecycle:
reuse records, launch/name/verify and update the registry once, without coupling
activation to unrelated workflow rewrites. Do not transfer the full conversation
or a directory of raw setup evidence.

## 6. Orient the user and close setup

Report a short, concrete result:

- What is configured and what is still unverified.
- Which live contact to open, its purpose and an actual available open/resume route.
- The useful opening question or next authorized action the contact has begun.
- Any remaining execution gate, distinguished from completed workspace setup.

Do not finish with "now prompt EL to set up the workflow" or require another skill
invocation to complete the requested setup. Prepare and route the next step. If a
platform or permission prevents it, state exactly what is blocked and retain the
setup checkpoint so this same skill can continue later.

Once the recipient accepts, stop routine setup-agent involvement. The user works
with the hierarchy; EL owns operations and can invoke a focused setup helper for
later changes. Keep the facilitator recoverable through its compact record, not
as an additional permanent supervisor.
