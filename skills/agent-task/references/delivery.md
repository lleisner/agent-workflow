# Review and delivery

The coordinator owns the result and may delegate detailed integration/checks.
Use the current project agreement for target branches, commands and gates.

1. Refresh assignment reports and actual Git state. Identify outstanding acceptance
   gaps, scope changes, uncertainty and resource implications.
2. Integrate selected ready contributions in the assigned task workspace. Do not
   pull unrelated unfinished work simply because it is on a convenient branch.
3. Run relevant checks and obtain required independent review. Give the reviewer
   the task, actual diff and acceptance/evidence, rather than an instruction to
   approve the implementer's conclusion.
4. Assess whether the result and approach still serve the broader scope. Resolve
   findings through the responsible structure; escalate beyond the grant.
5. Prepare a concise PR explaining the resulting behavior, checks, limitations and
   task link. Apply the configured approval gate before merging.
6. Verify actual integration on the intended target and update the authoritative
   task/report record. Mark stable promotion separately when applicable.

TC-to-AC integration can finish a task even while the area awaits project
integration, if that is the task's agreed acceptance target. Never imply a stable
release from a task/area merge alone.

Workers, coordinators and EL may each have integration worktrees. Combined roles
can collapse stages. Keep workspace allocation independent of approval policy.

Scope-local technical choices and dependency scheduling remain coordinator
judgments. Use small evidence lookups or delegate substantial investigation to
avoid filling leadership context with implementation details.
